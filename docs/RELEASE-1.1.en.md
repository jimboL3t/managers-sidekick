## History

Open **History** in the calendar. **Month snapshot** stores the selected month with its current team/employee names, duty times, rules, skills, availability, leave categories, holidays, assignments and locks. Enter a description such as “Published September”. A snapshot is also saved automatically **before each calculation**, including Another combination. Existing snapshots are not rewritten by later configuration changes.

Select an entry to view its read-only schedule or export a PDF using the frozen settings. **Restore as new team** creates an independent test team containing that month, leaving your current team untouched. Snapshots persist within `data/sidekick.json` and are included in backups. They are retained without automatic expiry, so file size grows with use. Deleting a team also deletes its history; a copied team retains independent history.

This is version history, not a per-click audit log, a separate published/draft status, or full undo. It cannot reconstruct older settings from before a snapshot existed. Capture a named snapshot when publishing or before manual changes you may want to reverse. Live calendars and annual totals still use current settings; use the history viewer/PDF for the frozen record.

## Employee availability

Open **Availability**, select an employee and tick the weekdays when they may work. Initially all weekdays are available, including for legacy employees. Add date exceptions, one per line:

```text
2026-10-05=0
2026-10-10=1
```

`0` means unavailable and `1` means available, overriding the weekly pattern. Dates must be valid ISO dates without duplicates. An empty exceptions area removes date overrides. This version models whole calendar days, not partial-day hours or employment contracts.

The scheduler excludes unavailable work dates, including supplementary assignments. An overnight shift checks both dates it touches; a shift ending exactly at midnight does not occupy the following date. Manual assignments and locked days remain preserved and conflicts are reported. Changing availability does not automatically recalculate.

Availability is not leave and does not automatically reduce the monthly work target. Rest can be assigned on unavailable dates up to the normal quota. If there are too few available dates to reach the target, the app reports the shortfall; enter actual leave separately where applicable.

## Native distribution with bundled Java

Use `scripts/package_native.py` on the **target OS and CPU architecture**. It builds/tests the portable release, stages only allowlisted files, and invokes JDK `jpackage`, which uses `jlink` to bundle Java. The destination computer does not need a separate Java installation for a native package. PDF still requires an installed Greek-capable font.

```sh
# Uninstalled application folder, available on all supported build OSes
python3 scripts/package_native.py --type app-image
# macOS build machine
python3 scripts/package_native.py --type dmg
# Windows build machine (use python if that is your Python command)
python scripts/package_native.py --type exe
# Linux build machine
python3 scripts/package_native.py --type deb
```

Build requirements: JDK 21+ with jpackage/jlink, Maven 3.9+, Python 3.9+ and OS packaging tools. Windows installer builds need a WiX version supported by the chosen JDK; Linux deb/rpm builds need their native packaging tools. Consult the [jpackage guide](https://docs.oracle.com/en/java/javase/25/jpackage/packaging-overview.html) and [command reference](https://docs.oracle.com/en/java/javase/24/docs/specs/man/jpackage.html). Cross-platform installers cannot be generated by simply running the Mac build for Windows. Build outputs go under `dist/native-<os>-<architecture>-1.1.0-<type>`. Existing output folders are not overwritten.

macOS packages are unsigned/unnotarized development distributions. Production distribution will require signing/notarization as appropriate and native installation/upgrade testing. Windows and Linux artifacts must be built and tested there before distribution. `app-image` is a runnable directory, not an installer: distribute the whole directory, not just its executable.

### Data location and migration

Native launchers use **`<user home>/ManagersSidekick/data/sidekick.json`** on all OSes (Windows typically `C:\Users\<user>\ManagersSidekick\data`). Portable ZIP launchers retain `data` beside their JAR. A custom `-Dsidekick.dataDir=/path` overrides the directory. The save status shows the absolute file path.

No automatic migration or merging occurs. Save/close the old app, back up its entire `data` folder and copy it to the native location before launching the installed version. Back up existing destination data first. All native versions share that user's directory: do not run them concurrently. Application updates should not be treated as data rollback; retain separate backups. The bundled documentation is also supplied in the portable ZIP.

## Fairness: proposed controls, not implemented in 1.1

A future fairness panel should offer separate night/weekend objectives, priority weights, lookback months and an explicit definition of a night duty. Employees should have separate participation toggles for each objective, with availability/skills respected before scoring. Exclusion from balancing would not prohibit those duties; “never assign nights/weekends” needs a separate hard restriction.

Compare eligible employees using capacity-adjusted targets rather than forcing equal counts across full-time, part-time or restricted employees. Preserve manual/day locks and report fixed imbalances. Show before/after counts and the cost of improving fairness versus coverage. Coverage, rest and availability stay constraints; fairness is an optimization preference unless an explicit hard cap is configured. The current algorithm does not yet balance nights/weekends separately.

## Why preview, undo and multiple backups would add value

Currently edits and completed calculations save automatically; not pressing Save does not protect the old schedule. History adds restore points, but a true preview would calculate on a separate draft with **Accept/Reject** before committing. Undo would reverse a recent accepted operation. Dated backups would protect the full dataset outside the active JSON, unlike history stored inside it or the single overwritten `.bak`. These three features remain proposals, not new buttons in this release.
